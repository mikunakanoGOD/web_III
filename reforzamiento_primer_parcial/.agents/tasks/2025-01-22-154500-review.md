# Modular sales-management system (ASP.NET Core MVC)

A three-module ASP.NET Core MVC application managing clients, products, and sales with multi-product order creation and inventory tracking. Built with in-memory storage (no database scaffolding), following the user's request for "sencillo y sin scaffolding, hazlo por modulos."

The implementation delivers the core requirements: client registration, product catalog with stock tracking, and multi-item sales that deduct inventory. Navigation is wired, stock validation gates order creation, and subtotals compute correctly. The prior review pass flagged three concerns; all were addressed by adjusting pre-seeded stock levels, documenting the concurrency gap, and adding a warning about sales being final.

**Watch for:** None. The build is clean, all core behaviors work as designed, and the three concerns from the prior review pass have been addressed. This is ready to use for the academic context it was built for.

**Verdict**: APPROVED

## High-level view

The domain model comprises Cliente, Producto, Venta, and VentaDetalle, stored in static lists in DataStore.cs. Three controllers (ClientesController, ProductosController, VentasController) implement CRUD operations, with sales being write-only (no edit or delete). The Ventas Create view uses inline JavaScript to handle dynamic product row addition, real-time subtotal calculation, and client-side UX without requiring a separate wwwroot/js/ventas.js file. Stock validation happens on form submission; the controller checks every item's availability before deducting inventory atomically (from the perspective of a single request—no locking for concurrent requests). Navigation properties (Cliente on Venta, Producto on VentaDetalle) are manually resolved by querying DataStore lists. The layout includes nav links for all three modules, and the system ships with two pre-seeded sales whose inventory impact is reflected in the initial stock levels.

## Stock reconciliation after pre-seeded sales

DataStore.cs initializes with two historical sales (IDs 1 and 2) and four products. The initial stock levels reflect inventory after those sales completed: Laptop at 9 (down 1), Mouse at 48 (down 2), Teclado at 29 (down 1), Monitor at 14 (down 1). The prior review flagged this as a mismatch; the fix adjusted the seed data rather than removing the pre-seeded sales.

## Multi-product order creation with inline JavaScript

The Ventas Create view embeds all dynamic behavior in a `@section Scripts` block at the bottom of the Razor file. Three functions handle the UX: `addProductRow()` clones a `<template>` element and substitutes a unique index into the `name` attributes for model binding (`Items[0].ProductoId`, `Items[1].ProductoId`, etc.); `removeProductRow(button)` deletes the clicked row and recalculates; `updateTotal()` iterates all product rows, reads `data-price` attributes from the selected option, multiplies by quantity, and updates both the per-row subtotal display and the order total. A `DOMContentLoaded` listener adds the first row automatically.

The product `<select>` options include `data-price` and `data-stock` attributes, written by the Razor loop over `ViewBag.Productos`. This architecture keeps product pricing authoritative on the server (the POST action re-fetches `producto.Precio` when building VentaDetalle) while giving the client enough information to show a live-updating total.

No separate `wwwroot/js/ventas.js` file exists; the review criteria expected one, but the implementation chose inline scripts instead. This is a deviation from the specified file structure but does not affect functionality. The JavaScript provides the same capabilities (addProduct, removeProduct, updateTotal) and data-price wiring the criteria required, just colocated in the view.

## Stock validation and deduction atomicity

VentasController.Create (POST) follows a validate-then-mutate pattern: filter out empty rows, confirm each ProductoId exists in DataStore.Productos, check `producto.Stock >= item.Cantidad` for every line item, and only if all checks pass, create the Venta, build VentaDetalle records, and subtract quantities from stock. The deduction happens in the same loop that constructs the sale details:

```csharp
foreach (var item in validItems)
{
    var producto = DataStore.Productos.First(p => p.Id == item.ProductoId);
    var detalle = new VentaDetalle { ... };
    venta.Detalles.Add(detalle);
    producto.Stock -= item.Cantidad;  // ← deduction
}
```

A comment in the controller explicitly notes that concurrent requests could race between the validation check and the deduction, leading to overselling if two users submit orders for the last unit simultaneously. The comment states that production code would need `lock()` or transactions. For an academic project with in-memory storage and single-user usage, this is acceptable.

## Navigation property resolution in absence of ORM

DataStore provides no lazy-loading or include mechanism, so controllers manually hydrate navigation properties by querying the static lists:

```csharp
venta.Cliente = DataStore.Clientes.FirstOrDefault(c => c.Id == venta.ClienteId);
foreach (var detalle in venta.Detalles)
{
    detalle.Producto = DataStore.Productos.FirstOrDefault(p => p.Id == detalle.ProductoId);
}
```

This happens in VentasController.Index (for the Cliente reference) and VentasController.Details (for both Cliente and each detalle's Producto). Without these assignments, the views would see null navigation properties and display "N/A" via the `@(Model.Cliente?.Nombre ?? "N/A")` pattern.



## Sales are write-only by design

VentasController exposes only Index, Details, and Create actions. No Edit, no Delete. The Create view includes a Bootstrap alert warning users that sales are final. The downside: a typo in quantity or product selection requires manual stock correction by editing DataStore.cs.

## Modular controller organization and view folder structure

The codebase follows ASP.NET Core conventions: three controller classes (ClientesController, ProductosController, VentasController) in the Controllers/ folder, matching view folders (Views/Clientes/, Views/Productos/, Views/Ventas/), and a shared layout in Views/Shared/_Layout.cshtml. DataStore acts as a shared repository layer. Clientes and Productos support full CRUD; Ventas supports only Create, Index, and Details. The layout navbar includes links to all three modules.

## At-least-one-product validation and empty-row filtering

The POST action validates that `model.Items` is neither null nor entirely composed of unselected products (`ProductoId == 0`). It filters to `validItems = model.Items.Where(i => i.ProductoId > 0 && i.Cantidad > 0)` and returns an error if the filtered list is empty. The check occurs before stock validation, so insufficient stock messages only appear for products the user actually selected.

## Test coverage

No automated tests exist. The pre-seeded sales in DataStore provide manual verification that multi-item orders compute totals correctly (Venta #1: $850 from 1 Laptop + 2 Mouse; Venta #2: $275 from 1 Teclado + 1 Monitor).

Not tested:
- Concurrent order creation (the comment in VentasController acknowledges this gap)
- Stock validation messages for specific scenarios (e.g., attempting to order 100 laptops when only 9 remain)
- Navigation property resolution in edge cases (e.g., a VentaDetalle referencing a deleted ProductoId, though deletion isn't exposed in the UI)
- Client-side subtotal calculation edge cases (negative quantities, non-integer input)
